## NVMeHA bench 慢速问题 + 两项修复（xnvme.c / xnvmeha.c / xnvmeha.h）

- 结论：bench 279 MB/s 是 MicroBlaze 喂队列的速度，不是 SSD——日志 `submit 100% / wait 0%`，每条 512 KiB 命令 ~1ms 的 PRP 构建（127 项 list + flush）是主因。
- **Timer 根因修正**：XSA/SDT/BSP 里 axi_timer_0 @0x41C00000 @100MHz 一直存在（pl.dtsi:440-460，xparameters.h:135）。之前"no working axi_timer"的真正原因是 `XNvme_TimerInit` 写 TCSR=LOAD|AUTORELOAD|ENABLE 后没清 LOAD——PG079 规定 LOAD=1 期间计数器不前进，TCR0 永远读 0。已改为两段写（load 后 release，对照 BSP xtmrctr.c:464-467），并修正失败提示文案。注意：新 dts 里 UART baudrate=230400（pl.dtsi:470），新 bitstream 的终端波特率要跟着改。
- **PRP 预构建缓存**（bench 路径）：
  - `xnvmeha.c`: 抽出 `XNvmeHa_BuildPrpInto()`（列表写入调用方存储、不刷 cache、返回写入项数）；原 `XNvmeHa_BuildPrp` 变薄封装；新增 `XNvmeHa_PushFullSqePrebuilt()` 与 `XNvmeHa_SubmitIoPrebuilt()`（PRP 模式专用，SGL 返回 -1）。
  - `xnvmeha.h`: 声明三个新 API。
  - `xnvme.c`: 新增 256 KiB 预构建存储（prp_lists 放 `.ddrbuf`——bss 与 stack 间隙仅 ~17 KB，不能放大数组；prp1/prp2 表共 4 KB 在 bss）。`XNvme_Bench` 在 pattern 生成后（计时窗口外）调用 `xnvme_bench_prp_prebuild()`，每 (ch, chunk) 一条 list，绝不共享给两个 in-flight 命令；`xnvme_bench_pass` 增加 prp1_tab/prp2_tab 参数，NULL 回退旧路径。覆盖 chunk >= 64 KiB（PREBUILT_MAX=128），更小 chunk 自动回退。
- XNVMEHA_AXI_MEM_DWIDTH 实际为 32-bit，64-bit push 路径不适用。
- 待验证：重编译后上板，期望日志出现 "TIMER: axi_timer @ 0x41C00000 ... TCR0 is counting" 与 "BENCH: prebuilt N PRP lists"；submit 占比应显著下降。
- 遗留：Fanxiang S500Pro TNVMCAP=0（疑似 booted ROM），与速率无关，另行处理。
- 编译修复：`XNvmeHa_SubmitIoPrebuilt` 调用 `XNvmeHa_PushFullSqePrebuilt(ha, ssd, sq, &sqe)` 漏传 prp1/prp2（xnvmeha.c:940），已补齐为 6 参数。DumpSsdMemory 里 w/i unused 警告为原有问题，未动。

## 第二轮上板结果（AXI timer 生效后）+ SW port 探针

- timer 修复生效：TCR0 counting @100MHz。真相：旧"279 MB/s"是 UART 秒表假象（CALL-limited 且波特率错配——自检实测 UART 实跑 ~12667 baud 而非假设的 9600/230400，bitstream 里 UART 分频器仍是旧的）。真实速率一直是 ~157 MB/s（16 MiB / 106.6 ms）。
- PRP 预构建已生效（prebuilt 32 lists），但 submit 仍占 91%（97.8ms/32 命令 ≈ 3.06 ms/命令）。每命令软件工作只剩 ~100 指令 + 16 次 Xil_Out32 + mbar，100MHz 下最多几十 µs → 嫌疑落在 AXI 写路径本身（swaxi port / interconnect 每笔单拍写延迟 ~190µs 量级）或 mbar 等待 posted write 全部退休。
- 已加 `xnvme_swport_probe()`（xnvme.c:1463，bench 前调用 xnvme.c:1860）：四项微基准——DDR store 基线 / IP reg read（非 posted，AXI 往返）/ SW port read（与 push 同一 slave）/ IP reg store+mbar（push 的实际形态）。目标是定位 3ms/命令 到底花在 AXI 事务还是 barrier。
- 待办：跑探针后按结果分流——若 store+mbar 慢 → AXI 路径问题（考虑 swaxi 位宽/interconnect 配置或 PL 侧 DMA 喂 SQE）；若只有 mbar 慢 → 去掉 PushWords 尾部 Dsb 或按批 mbar。

## 探针结果（第三轮上板）+ timer 自校准

- 探针结论（timer tick 单位，比值可信）：SW port read = 2.11 ms/次，IP reg read = 46.7 µs（同一 fabric，swaxi slave 慢 45 倍），DDR store+add = 17.3 µs，reg store+mbar = 74 µs。submit 3.06 ms/命令 = 16 次 swaxi 单拍 store + mbar（每 store ~190 µs）→ **swaxi port 是绝对瓶颈**。
- 17.3 µs 的 DDR store 在 100 MHz MicroBlaze 上不可能 → 整个时钟树实际频率与 XSA 不符（与 UART 18.27x 错配互相印证）；绝对时间需标定。
- 旧自检 bug：exp_us/imp_baud 漏乘 10 bits/byte（512B@230400 应为 22.2 ms，打印成 2.2 ms），导致 18.27x 的 ratio 混淆了"波特率错配"和"时钟树错配"两种解释。已修正。
- 已实现 timer 自校准：`XNVME_UART_GROUND_BAUD`（默认=XSA 波特率 230400，用户需改成终端实际波特率）作基准，自检算出 `xnvme_timer_hz_real` 并全程采用（XNvme_TimerUs / xnvme_bench_to_us / PROBE_NS / bench 打印全部切到 `xnvme_timer_hz_eff()`）。若终端=115200 → timer≈91 MHz（数字基本成立）；若=9600 → ≈7.6 MHz（真实吞吐 ~12 MB/s）。
- 100 行 "INT SW CQ read with none available" 是探针 100 次空 CQ 读的预期副作用，无害。
- 下一步：用户确认终端波特率 → 设置 XNVME_UART_GROUND_BAUD 重编译；检查 BD 中 NVMeHA SW AXI4 位宽与 C_SW_FULL_CMD 配置（单拍写 vs 16-beat burst 的病态延迟）；终极解法 PL 侧 DMA 喂 SQE。

## 第四轮：波特率真相澄清 + 撤销错误校准 + hwh 结构实锤

- 用户终端（XCOM）= 230400 且显示正常 ⇒ 线上真是 230400 ⇒ **bitstream 是新的，无需重新生成**。
- hwh 实锤（top_ku040_add_timer.xsa, 今天 10:33）：axi_timer_0 与 axi_uartlite_0 共享 ddr4_0_addn_ui_clkout1 = **100 MHz**；UART C_BAUDRATE=230400；MicroBlaze Clk = 同一 100 MHz（nvmeha clk_axi_lite=100M ui_clkout1、clk_core=200M ui_clkout2，无异步 CDC）。
- **"UART 实跑 12667 baud / 18.18x off"是自检测量假象**：512 字节轮询循环里每字节要等一次非缓存 MMIO 状态读（~36 µs），40.4 ms = 线上 22.2 ms + 轮询开销 ~18 ms，与 PROBE 2 的 46.7 µs MMIO 读延迟吻合（512×(43.4+36)µs≈40.5ms）。**Timer 就是 100 MHz，XSA 正确，第三轮所有测量值（155 MB/s、SW port 2.11 ms、submit 91%）都是真实时间，不乘 1.82。**
- **撤销上一轮加的 timer 自校准**（dt*baud/(i*10) 会被轮询开销污染成 182 MHz，导致所有时间偏乐观 1.82 倍）。已重写 `XNvme_TimerSelfTest`：不采用校准值，改为把 40ms 窗口拆解成"线上时间 + 轮询开销"打印解释；xnvme_timer_hz_real 不再被赋值（恒用 XNVME_TIMER_HZ）。
- **BD/XSA 参数确认**：`C_SW_FULL_CMD=1`（design_1.hwh:34904）、`C_AXI_MEM_DWIDTH=64`、`C_EN_HW_IF=0`、`C_NUM_SQ_SW_0=4`。swaxi 0x44A00000 = nvmeha S_AXI **直连 MicroBlaze M_AXI_DC（32-bit）**，不经 SMC。即：32-bit 单拍写 × 16 打进 64-bit full-cmd FIFO —— 病态组合确认。
- 下一步候选：(a) PL 侧 DMA/状态机喂 SW 口（终极）；(b) 用 ILA 抓 swaxi wready/awready 看 IP 为何每拍拉长；(c) 评估 C_SW_FULL_CMD=0 的可行性。

## 第五轮：PG328 原文核对 + 架构方向确认

- 用户确认目标架构：MicroBlaze 组队列（构建 SQE/PRP 写 DDR），退出数据面 —— 与 PG328 SW interface 设计意图一致，Figure 13 参考设计拓扑（MicroBlaze 直连 S_AXI）本就是标准形态。澄清：问题从来不是"直连拓扑"，而是实测每笔事务 ~190 µs 的异常延迟（正常 AXI slave 为几十 cycles）。
- PG328 原文确认（docs.amd.com 全文检索）：SW 推 SQE 走 AXI4 mem-mapped、HW 推 SQE 走 AXI4-Stream；SW_FULL_CMD/HW_FULL_CMD 选 64B 全命令 / 32B 部分命令；**partial 模式 + PRP 不能用 PRP list/多页（必须 SGL）→ 用户 512KiB PRP 传输下 partial 模式不可行**；CQE 读取在 AXI_MEM_DWIDTH=64 时 4 cycles（CQ 读 2.1ms 同样是异常的一部分）。
- 章节位置：HW Application Interface 在 Chapter 3 Product Specification（PDF 约 p.14-15）；Figure 13 Reference Design 在 Example Design 章（约 p.25）。在线 portal 不显示页码，以 PDF 目录为准。
- 推进路径定序：先 ILA 抓 swaxi aw/w/b 三通道 ready/bvalid（区分 IP 拉长 vs fabric 问题）→ 再定 SQE push 归属：PL DataMover/DMA 8-beat burst 推 S_AXI（MicroBlaze 只写 DDR 环形缓冲，ns 级）或启用 HW AXI4-Stream 接口。注意 hwh 里已有 axi_dma_0@0x41E00000（挂在 M_AXI_DC 上，流侧疑似空闲），可评估复用。
